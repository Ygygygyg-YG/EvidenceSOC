# Task13 controller and isolated worker implementation

The runner implements the P1/P4 boundary from the Task13 design. Importing the CLI or creating a plan does not call a model. Fixture mode is explicitly synthetic, returns unknown, and is refused for the test split. This document describes implemented behavior; passing offline tests does not establish a real model or completed formal experiment.

The accepted AIT neutral input root is `.backups/task12-readiness/data/ait/cases/test`; `data/ait/cases/test` contains preserved legacy names and must not be used. DEDALE input root is `data/dedale/priority-cases-v4/test`. Their frozen selection SHA256 values are respectively `bbabb8b072c29a770863c4a6a88537e446305ba7006ff40afa2cf1229fdbbd3b` and `047c2887a8057a348fc0c07fd6c3773c9e61f39302f7f9d4b1f4979d4e9b5c79`. DEDALE preparation files retain `prepared_not_frozen`; the bound Task12 external freeze receipt supplies acceptance authority.

## Controller phases

`python -m evals.runners.cli plan --config <controller.json> --output <new-plan.json>` creates the full eight-group matrix from the selected cases. The plan binds controller configuration, selection, admissions, agent manifests/events and scoring-side files. Worker specs contain no paths, dataset labels, gold, scenario descriptions or other case directories. Case identities must be neutral; the agent mount permits exactly `manifest.json` and `events.jsonl`.

`python -m evals.runners.cli execute --plan <plan.json> --output-root <attempts> --runtime-config <runtime.json>` dispatches one worker at a time. `--row-limit` supports measured development batches. `--fixture` is an explicit model-free pipeline check for development/validation. There is no host or fixture fallback when Docker is unavailable.

Each row has `attempt-001/started.json`, `result.json` and `attempt.json`, written exclusively without replacement. A crash after the start record remains interrupted. Resume retains completed/failed rows. Every scoring pass retains every planned row, including missing rows. Attempt 2 requires `authorize-rerun` followed by `execute --rerun-permit`; its immutable permit binds the plan, row, previous attempt hash, approving identity/time and infrastructure/transport reason. Schema failure, application failure, completed unknown or low scores cannot authorize a rerun. The final allowed attempt supplies the diagnosis; all attempts contribute usage/cost.

Readiness checks the shared account before each new attempt. A halted account, exhausted campaign balance, or exhausted development allowance stops dispatch while later rows remain missing. Changed agent input is rejected before creating an attempt directory. Unregistered attempt directories are rejected rather than silently omitted. If an interrupted attempt has unknown usage or duration, an authorized successful rerun cannot turn the combined totals into exact known measurements.

Tool-ledger completeness is also normalized across all attempts. Missing/interrupted results or an explicit failed ledger export make the row incomplete. A successful empty export remains a known zero; older results without the flag require an explicit ledger list. The normalized boolean is passed to resource metrics, which retain unknown totals and observed subtotals separately.

`python -m evals.runners.cli score --plan <plan.json> --output-root <attempts> --output <new-score.json>` starts a separate scoring process. Only this process reads gold. DEDALE uses frozen `case_is_attack` and masks. AIT uses frozen per-event binary/six-class labels and does not invent ATT&CK or stage gold. Human review is absent/null unless imported through `evals.review.validated_reviews`. Scores remain automatic intermediate results; the CLI does not certify G6/G7 or the overall Task13 outcome.

## Worker export and dependencies

`python -m scripts.task13_worker_runtime export-source --commit <full-SHA> --destination <new-source-dir>` exports only backend source, contracts/adapters and the two runtime helpers from the fixed commit. Exported files and the archive are rechecked against `git archive` on the controller. Repository roots, Git metadata, docs, tests and scoring modules are not exported. New code must be committed before it can enter a real worker; source export has no current-working-tree fallback.

`python -m scripts.task13_worker_runtime prepare-dependencies --python-version 3.12.14 --destination <new-Linux-packages-dir>` exports the unchanged project lock and installs only hashed binary wheels for `x86_64-manylinux_2_28`. It writes `task13_dependencies.json` binding the project lock, requirements, Python ABI and installed file tree. The worker checks the full tree and its interpreter version. A failed preparation retains its directory for diagnosis; use a new destination for another attempt.

Runtime JSON requires `source_dir`, `source_commit`, immutable `image_id` (`sha256:` digest), `network`, `dependencies_dir`, `dependencies_lock_sha256`, `knowledge_dir`, `knowledge_sha256`, shared `budget_dir`, independent `output_dir` and `phase`. `knowledge_sha256` is produced by `scripts.task13_worker_runtime.dependency_tree_hash`. The dependency receipt uses the same function while excluding its own receipt filename. Phase must match development/formal selection and cannot bypass the development cap. `budget_dir/campaign.sqlite` is shared across datasets and all phases, never reset for another batch.

The explicit inherited credential/service names are `DEEPSEEK_API_KEY`, `DATABASE_URL`, `OPENSEARCH_URL`, `OPENSEARCH_INDEX`; values are not placed in command arguments or logs. No `.env` is mounted or implicitly read by the runtime. The adapter receives `TASK13_BUDGET_DB=/app/budget/campaign.sqlite`, `TASK13_OUTPUT_DIR=/app/output`, `TASK13_PHASE`, the nonce and the validated `TASK13_SOURCE_COMMIT`, which binds retained B3 approval resources to their implementation.

## Isolation and final gates

Docker uses a digest, `--pull=never`, non-root UID65532, read-only root, no added capabilities, no-new-privileges, private PID namespace and explicit memory/CPU/PID bounds. Agent, source, spec, bootstrap, dependencies and knowledge mounts are read-only. Only the exact campaign-budget and current-case-output directories are writable; no repository root or sibling case is mounted.

Before any model call, the same Python PID reads legitimate input, attempts scoring/Git/other-case canaries, and emits nonce/PID/hostname/input hash. It waits for `GO:<nonce>`. The controller inspects the running container, exact mounts/flags/image, checks PID1 and the probe binding, and then releases the adapter. Each model ledger record must match that PID, nonce and hostname. Task12's model-free probe alone is insufficient. Database/index cross-case denial is an additional adapter/service acceptance requirement.

Formal dispatch requires explicit `--allow-final-test`, exactly22/66 selected cases, matching Task12 admission, a complete hashed freeze, passed G1–G5, a bound real-model isolation receipt with zero critical skips and cross-case denial, and the committed tested implementation. Freeze `bindings` must include protocol/dependencies/knowledge/model/prompts/tools/scoring/review/plots/dataset_admission; `files` must cover every evaluated backend source and test, every evaluation source/test/config seed, controller scripts, protocol, project dependency metadata and lock. Missing files, changed hashes, changed committed sources and untracked evaluated sources (including Git-ignored source) fail. The isolation receipt must bind the source commit and real model invocations. Missing gates fail before dispatch.

`evals/configs/ait.json` and `dedale.json` are deterministic real-input seeds with no accepted freeze. They retain the pre-Task13 source HEAD and cannot dispatch formally. `python -m evals.freeze --source-commit <tested-HEAD> --run-id <campaign> --output data/task13/control/<campaign>` generates fresh controls and a `prepared_not_frozen` manifest, leaving G1–G5 pending and isolation absent. These generated control artifacts are outside committed source, preventing circular source-commit/config/freeze hashes. The generated freeze manifest and test scratch are excluded from source coverage; committed seed configs remain included.

`evals/run_formal.ps1 -Dataset ait|dedale -AllowFinalTest` expands plan/execute/score, records exact command arguments and configuration hashes, and stops on a nonzero phase. Runtime and controller files must already exist; no final gate or human approval is generated by the script.

Default formal output is `data/task13/runs/<dataset>/<run-id>`, allowing one campaign run ID for both datasets. Explicit output roots are honored. Docker startup, missing probe, failed inspection and unexplained process exit now retain a typed infrastructure category; communication interruptions retain transport. Bootstrap errors are serialized as sanitized structured results. Any reported schema/refusal/application failure blocks rerun eligibility even when a later error is transport; completed unknown or low-score rows are never rerun triggers.

Every invocation, including a resumed invocation, also writes a separate immutable `commands-<invocation-id>.json` recording that invocation's score path and whether its plan was reused. The original `commands.json` retains the initial configuration binding.

The separate F8 callback is `scripts.task13_worker_runtime.run_verification_container(request, agent_dir, options)`. Its dedicated `task13-verification-worker-v1` request is validated by `evals.adapters.verification_worker`; condition/truth/branch labels are refused by that schema. It uses the same committed source, dependency hashes, exact mounts, image inspection and PID1 handshake. Its output namespace is `verification/<case-id>/<request-id>/<nonce>`. The worker receives service credentials without a model API key and enters only the original validator after inspecting the request. A model ledger in its returned result is rejected. Persisted product approval, unexpired plans and separate database/index/checkpoint/trace resources remain additional F8 controller/adapter requirements; a synthetic approval fixture does not satisfy them.

`run_source_review_container` accepts only `task13-source-review-worker-v1` and dispatches the adapter's `SourceReviewRequest`/`run_source_review`. It binds the request source commit and agent-input hash before startup and retains output under `source_review/<case-id>/<request-id>/<nonce>`. All source-review operations use verification phase; only `renew_plan` receives the model credential. `read_packet` and a user-supplied `decision` are model-free and reject returned model ledgers. Source-review operations retain the same inspected mounts, PID/nonce/hostname checks and shared campaign account; the runtime does not approve any plan.
