# EvidenceSOC 前端完整设计与实施方案

版本：1.2。编写与审查日期：2026-09-27。状态：已完成设计可行性审查，并同步重做本地模拟预览；业务实现、版本组合联调及长时间运行验收尚未完成。

本方案以现有 EvidenceSOC 仓库为基础，面向比赛演示和日常安全调查两种使用场景。交付物为本文档及 `docs/frontend-previews` 中的模拟 HTML、PNG 和检查资料；本次不修改业务代码，不安装依赖，不执行 Git 提交、推送或上传。

**选型硬约束：开源、免费、自托管可用。**第一版所有前端功能均使用免费开源依赖实现，不要求 React Flow Pro、商业后台模板、托管测试平台或付费模型 API。软件许可费用为零；用户自有设备或服务器的运行成本单独计算。

### 本轮审查结论

**可行，可以作为实施依据，但需采用本稿明确的响应式和交互约束。**三级表面、细边框、统一语义色、固定导航与状态栏、网格总览、攻击链证据联动、人工审批和规范展示页，都能通过现有免费开源组件与 CSS 实现。主要复杂度在数据契约、实时恢复、证据完整性与审批一致性，不在深色外观。

| 审查项 | 判断 | 本稿采用的调整 |
|---|---|---|
| 专业深色、扁平微质感 | 可直接采用 | 三种中性表面、1px 边框；无外投影、玻璃模糊、霓虹和装饰动画 |
| 严重用暗红、辅助文字较弱 | 有条件采用 | 暗红用作标签底色，文字保持可读；辅助文字降低强调程度，不靠过低对比度 |
| 调查页 `3:6:3` | 宽屏可行 | 作为宽屏默认比例；容器不足时改两栏加右侧抽屉，不强行压缩画布 |
| 审批页 `7:3` 与常驻按钮 | 桌面可行 | 右栏设最小宽度和独立滚动；按钮在卡片底部，避免覆盖理由输入与正文 |
| 数据源健康全局置顶 | 可行，需统一数据 | 顶部显示健康摘要；首页详细模块使用同一查询与更新时间 |
| 工作流全部横向 | 可行，需区分历史记录 | 六角色、审批过程、响应过程横向；活动与审批历史仍可纵向 |
| 一屏中高密度 | 可行，不能以缩小正文实现 | 紧凑行高、抽屉和展开行；14px 业务正文、完整值可访问 |
| 企业级与 7×24 运营 | 界面目标可行，运行能力尚未证明 | 连续运行、权限、审计、依赖监测和恢复需另行实测；深色截图不构成生产可用性证明 |

本轮使用 frontend-design 重做第 18 节的预览，颜色、页面结构和交互规则与本文 1.2 版同步。HTML 可以演示查看、筛选、联动与确认；静态 PNG 只展示初始画面。所有页面数据均为样例，不连接实际业务接口。

## 1. 推荐方向与交付目标

推荐建设一个“证据驱动的安全调查工作台”：首页帮助发现需要处理的问题，调查页展示攻击行为、证据依据和六角色执行过程，响应页完成有记录的人工审批与模拟验证。

### 目标用户、核心任务与内容特点

| 页面 | 主要用户 | 核心任务 | 内容特点与设计决定 |
|---|---|---|---|
| 运营总览 | 当班 SOC 分析师 | 发现高风险、长等待与异常接入，进入优先调查 | 四项待办紧凑置顶；队列按严重性和等待时长排序；趋势、状态和健康用于辅助判断 |
| 调查工作台 | 安全调查分析师 | 核对攻击步骤、证据和未证实关系 | 观察时刻、主机、证据编号与查询需要对应；主画布最大，右侧证据随选中步骤联动 |
| 响应审批 | 有审批权限的负责人 | 看清动作、影响、回滚和验证，再决定方案 | 左栏按决策问题组织模块；右栏保留版本、理由与唯一操作行 |
| 设计规范 | 前端开发与评审者 | 检查色值、密度、语义及组件状态 | Token、状态三态、表格、输入与焦点集中展示；正式产品不在普通导航开放此入口 |

视觉方向采用“证据链阅读台”：辨识度来自同一案件的观察时刻、证据引用和人工决定之间的联系。结构、编号、色彩和动效都解释业务内容，不增加营销式大标题、装饰编号或无关视觉元素。具体设计取舍见 [预览设计说明](frontend-previews/DESIGN.md)。

第一版用户应能完成以下闭环：

```text
运营总览 → 告警列表 → 告警详情 → 启动调查
                                  ↓
调查工作台：事件摘要 + 攻击链 + 证据详情 + 六角色横向进度
                                  ↓
响应方案 → 人工批准或拒绝 → 模拟处置 → 效果验证 → 调查归档
```

三种可行方向的取舍如下。

| 方向 | 优势 | 成本或局限 | 本方案采用方式 |
|---|---|---|---|
| 大屏为中心 | 适合展示运营规模和整体趋势 | 容易堆砌图表，实际调查需频繁跳转 | 首页保留少量有操作价值的指标和图表 |
| 表格后台为中心 | 告警筛选、分页和审批开发快 | 攻击行为与证据关联不够直观 | 用于告警、调查列表和审批队列 |
| 调查工作台为中心 | 能清楚解释系统结论和证据来源 | 需要认真设计图谱、时间线和数据恢复 | 作为核心产品界面，优先完成 |

### 1.1 第一版必须实现的内容（P0）

- 统一深色主题、响应式框架及加载、空数据、失败、重试状态。
- 运营总览、告警列表、告警详情、调查列表、调查工作台、响应审批与验证。
- 六个逻辑角色的真实执行状态、结构化结果与证据引用。
- 攻击链图及可替代的阶段列表；节点到证据详情的联动。
- 批准与拒绝模拟处置、方案版本检查、重复提交处理。
- SSE 增量更新、刷新恢复、断线重连及数据过期提示。
- 无云模型密钥时，以明确标识的规则模式走完整闭环。
- 基于固定数据的自动化验收，以及至少一条真实后端集成闭环。

### 1.2 第二阶段增强（P1）

独立证据检索页、审计检索页、数据源管理页、评测结果页、服务端报告导出，以及完整账户与角色管理。每项均需对应后端接口和验收后再加入导航。

自由编辑攻击关系、复杂拓扑分组、多人协同编辑、实时地理地图、完整 ATT&CK 矩阵和浅色主题不进入第一版。第二阶段也先根据用户需求选择其中的具体功能，不一次性引入全部能力。

## 3. 视觉系统

### 3.1 整体风格

面向安全分析师持续值守的企业级 SOC 工作控制台，采用深蓝灰画布、三级表面、克制的青蓝操作强调和统一状态标签。信息密度中等偏高，通过底色深浅、1px 细边框、字号和规范间距区分层级。图表和攻击链承担信息表达，不增加无业务意义的装饰。

卡片圆角统一 8px；普通卡片、抽屉、弹窗、菜单均不用外投影。微质感最多使用一条很弱的内侧边线，例如 `inset 0 1px 0 #263247`，它不是主要分层手段。禁用玻璃拟态、`backdrop-filter`、霓虹光晕、大面积渐变、纯黑和纯白视觉填充；模态遮罩使用深蓝灰半透明层。键盘焦点使用可见 outline，不用发光阴影。

默认固定深色，第一版不随操作系统自动切换。数据阅读和审批在同一视觉体系下完成。进入演示模式时只隐藏不必要导航，颜色和状态语义保持一致。

### 3.2 基础颜色 Token

| Token | 色值 | 用途 |
|---|---|---|
| `bg.canvas` | `#0B1220` | 页面、图谱画布底色 |
| `bg.surface` | `#111B2E` | 导航、卡片、表格 |
| `bg.elevated` | `#17243B` | 抽屉、弹窗、菜单及选中态；第三级表面 |
| `text.primary` | `#F1F5F9` | 标题、关键内容 |
| `text.secondary` | `#B6C4D8` | 正文和说明 |
| `text.muted` | `#8B9CB5` | 时间及次要标签 |
| `border.decorative` | `#2B3C55` | 卡片分隔、辅助网格 |
| `border.control` | `#657E9E` | 输入框及可交互控件必要边界 |
| `accent.primary` | `#4FAFC2` | 克制青蓝；主按钮、可操作链接、选中标识与焦点 |
| `accent.hover` | `#65C1D2` | 主按钮悬浮 |
| `accent.active` | `#3994A8` | 主按钮按下 |
| `focus.ring` | `#4FAFC2` | 2px 键盘焦点环，外偏移 2px |

中性背景只有 `canvas → surface → elevated` 三级，不额外引入第四种选中表面。选中行和导航使用 elevated 底色，加青蓝边线、图标或文字；不能仅凭底色区分选中。主按钮使用独立的操作色，不算第四种中性表面。青蓝仅强调可操作元素、焦点和选中态，不为普通标题、指标数字和大面积卡片铺色。

主按钮用青蓝背景和 `#0B1220` 文字。文字强调顺序为主要 `#F1F5F9`、正文 `#B6C4D8`、辅助 `#8B9CB5`；辅助信息的“较浅/较弱”解释为视觉强调较低，不使用比标题更亮的文字，也不压低到难以阅读。普通正文避免额外透明度，通过专用 Token 调整层级。

正文和状态前景色相对最亮常规表面 `#17243B` 的对比度目标为至少 4.5:1；控件必要边界目标为至少 3:1。装饰边框不满足功能边界要求，因此不能用作输入框唯一边界。选中底色、悬浮层和标签底色需分别验收，不通过降低整块容器透明度实现。

本稿按所有普通业务文字至少 4.5:1 的更统一目标验收；这是对可读性的要求，不能据此直接证明长时间观看不会疲劳。[W3C 文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

| `high` | 高 | `#FFB07C` | `#39291F` |
| `medium` | 中 | `#F6C76B` | `#342E20` |
| `low` | 低 | `#8DBBFF` | `#1D2B43` |
| `info` | 信息 | `#B6C4D8` | `#263247` |

| 执行/业务状态 | 前景色 | 视觉表达 |
|---|---|---|
| 运行中 | `#8DBBFF` | 转动图标 + 状态文字；减少动态效果时静止 |
| 待处理 / 待审批 | `#F6C76B` | 时钟图标 + 精确业务名称 |
| 调查完成 | `#76D7AE` | 勾选图标 + 调查完成；单列显示验证结果 |
| 执行失败 / 验证失败 | `#F2A0A5` | 错误图标 + 所属阶段及失败原因 |
| 待人工复核 | `#F6C76B` | 人工图标 + 待复核 + 原因；属于等待人工处理 |
| 已拒绝 | `#B6C4D8` | 停止图标 + 已拒绝；显示理由 |
| 未知/证据不足 | `#8B9CB5` | 问号图标 + 明确文字 |

执行和验证成功均使用绿色 `#76D7AE`，进行中使用蓝色 `#8DBBFF`，等待人工处理使用金黄 `#F6C76B`，失败使用红色 `#F2A0A5`。已拒绝属于人工决定，不自动当作执行失败。严重性的信息级使用灰色，不复用低危的浅蓝；主题实现需分开 severity.info 与 execution.running。

严重标签通过暗红底色表达严重程度，不能把暗红小字直接放在深色卡片上。严重性与业务状态允许复用色系，但必须采用独立 Token、明确文字、不同图标和分列显示，避免把“中危”和“待审批”读作同一含义。

证据支持的攻击步骤使用实线边框；候选步骤使用虚线及“待证实”文字；证据缺失使用问号及说明。**存在 Evidence ID 不自动代表结论已证实，置信度也不是经过校准的真实发生概率。**

严重性、调查执行状态和验证结论分别占用不同字段。高危事件可调查完成，但验证失败；证据不足也不能显示为低风险或安全。

### 3.4 字体、尺寸与组件密度

| 元素 | 字号 / 行高 | 规则 |
|---|---|---|
| 页面标题 | 24 / 32px | 每页一个主标题 |
| 区域标题 | 16 / 24px | 中等字重 |
| 正文、表格 | 14 / 22px | 关键业务文字不得缩到 12px |
| 辅助标签 | 12 / 18px | 用于时间说明和次要提示 |
| 指标数字 | 28 / 36px | 等宽数字，必要时显示单位 |
| IP、ID、哈希、查询 | 13 / 20px | 等宽字体，完整值可复制 |

中文字体优先系统字体：`Microsoft YaHei UI`、`Microsoft YaHei`、`PingFang SC`、`Noto Sans CJK SC`、`sans-serif`；等宽字体为 `Cascadia Mono`、`Consolas`、`monospace`。第一版不用在线字体，避免离线演示和生产构建依赖外部字体下载。

间距 Token：4、8、12、16、24、32px。卡片圆角 8px，输入框与按钮 6px，标签 4px。普通控件高度 36px；触屏主要点击目标至少 44px；桌面表格默认紧凑行高 40px，用户可切换舒适行高 48px。卡片默认内边距 16px，图表和长文模块可用 20/24px；审批的紧凑详情模块可用 12px。同类卡片保持一致，间距减少不能以裁切正文为代价。主要区块间距 16px，审批紧凑模块间可用 12px，页面外围 24px。

不为凑一屏而缩小关键业务文字；长标题允许两行或展开查看。高密度优先通过减少空白、列优先级、服务端分页和局部详情实现。

响应用户动作的过渡持续 140～180ms：按钮状态、步骤选中、导航/证据抽屉与确认提示。尊重 `prefers-reduced-motion`，减少动效时立即完成状态切换；不采用卡片逐个飞入、持续闪烁、页面自动滚动和全量数字跳动。静态图片不展示动效，交互以 HTML 为参考。

### 3.5 主题落地方式

创建一个 `socTokens.ts` 作为所有业务 Token 的唯一来源，派生出 Ant Design ThemeConfig、CSS 变量、ECharts 图表选项和 React Flow 自定义节点样式。

- Ant Design：`ConfigProvider` 使用 `theme.darkAlgorithm`，覆盖表面、文字、边框与主色；通过组件 Token 调整表格、抽屉、弹窗和输入框。
- 同时覆盖弹出组件的背景与阴影配置，并检查实际计算样式；仅应用 darkAlgorithm 不保证没有默认外投影、纯白文字或错误的严重性颜色。
- 消息与确认：使用 `App` 上下文实例，避免静态 message/Modal 调用绕过主题。
- Next.js：根布局使用 `AntdRegistry` 注入首屏样式；包含主题、QueryClient 和状态的 Provider 使用客户端边界。
- React Flow：设置暗色模式，同时显式应用业务节点、连线与背景 Token。
- ECharts：显式设置图表背景、文字、轴线和系列颜色，不假定图表自动继承 Ant Design。
- Tailwind：负责尺寸、Grid 和断点，引用同一 CSS 变量，不另外维护一套状态色。

Ant Design 官方支持上述主题与首屏样式方案。[主题说明](https://ant.design/docs/react/customize-theme/)、[Next.js 接入](https://ant.design/docs/react/use-with-next/)

### 3.6 设计规范展示页

将规范展示作为 M0 的开发资料，使用与业务页面同一组 Token 和组件。可使用开发环境独立的 `/design-system` 页面；生产环境不在分析师导航展示此入口。静态预览保留在 `docs/frontend-previews`，无需商业设计工具。

采用网格卡片排布：背景与表面色卡、三级文字样例、按钮默认/悬浮/按下态、严重性标签、业务状态标签、紧凑表格行、输入框默认/焦点/错误态。每块注明 Token 名、精确 HEX、尺寸和使用范围，并补齐键盘焦点、选中、禁用及加载态。

同时展示抽屉/弹窗、矩形图谱节点、实线与虚线箭头、横向步骤条以及图表轴线与图例。示例必须能核对实际颜色和交互状态，不只是一张无法检查状态的色卡图片。

## 5. 全局布局与响应式

### 5.1 桌面外壳

桌面使用 64px 高的固定通栏状态区（跨整个视口），其下左侧为固定 64px 窄导航；各业务页面保持相同位置，不因路由切换改变宽度。图标提供可访问名称、悬浮文字与可展开的文字菜单；展开菜单作为浮层，不推挤业务布局。主内容从顶栏和导航之外开始，左右各 24px 内边距，调查与审批页使用全部可用宽度。

常驻位置约定：导航在左，连接与源健康在顶，证据详情从右侧进入；提交、批准、下一步等工作流主操作在所属工作区或决策卡的底部右侧。时间筛选、刷新、图谱缩放等辅助操作保留在各自工具条。首页不强行增加一个没有业务作用的右下主按钮。

主操作区属于布局中的专用行或卡片底栏，使用表面色及顶边线分隔，不用悬浮投影。需要常驻时采用 sticky 或父容器内固定区域；正文预留对应空间，不能用绝对定位把按钮盖在正文上。移动端和高倍缩放下优先保证内容与表单可读，按钮回到模块末尾。

运营页采用自然纵向滚动。调查页采用自适应画布与下方横向角色进度：普通桌面画布至少 360px 高，900px 屏幕建议约 400～440px，1080px 屏幕约 520～560px；高度不足时继续纵向滚动。不能把所有业务页固定为 1080px 高并用 overflow:hidden 裁掉内容。

### 5.2 调查工作台的尺寸

| 屏幕 | 内容宽度计算 | 布局 |
|---|---|---|
| 1920px | 1920 − 64 − 48 = 1808px | 扣除两段 16px 间距，按 `3:6:3` 分配为 444px 上下文 / 888px 主区 / 444px 证据检查器 |
| 1440px | 1440 − 64 − 48 = 1328px | 240px 上下文 + 16px + 1072px 主区；证据用右侧 440px 抽屉 |
| 1280px | 1280 − 64 − 48 = 1168px | 240px 上下文 + 16px + 912px 主区；证据使用右侧抽屉 |

上述为未扣除浏览器滚动条等差异的尺寸计算样例。宽屏默认 `3:6:3`，中间占一半，左右各四分之一；“左轻右辅”通过内容层级实现，并不意味着两侧必须等量填满。真正的三列/两列切换依据工作台容器可用宽度：至少 1500px 时三列，1000～1499px 两列，低于 1000px 单列/页内标签。浏览器缩放和滚动条均会改变容器宽度，不能只判断物理显示器尺寸。

若在 1440px 强行保持三栏比例，主区仅约 648px；1280px 下证据栏仅约 284px，均不适合作为默认值。因此 `3:6:3` 是宽屏参考比例，不是所有视口的硬约束。1920px 的 888px 中栏也只够三个 240px 节点、两段 64px 间距和 40px 内边距，不保证完整长攻击链同屏；保留画布内平移、阶段筛选与列表视图。

1920px 证据检查器为非模态侧栏；1440px 抽屉为模态面板。抽屉打开时保留图谱选中状态、缩放和位置；关闭后焦点回到触发它的节点或证据按钮。

### 5.3 窄屏规则

| 视口宽度 | 处理方式 |
|---|---|
| 1280～1599px | 固定窄侧栏；上下文可折叠；证据抽屉 |
| 1024～1279px | 上下文移到页头折叠摘要；主画布占满 |
| 768～1023px | 菜单抽屉；“概览/攻击链/角色/证据/响应”页内标签 |
| 小于 768px | 指标两列；告警改紧凑卡片；攻击链默认阶段列表；证据与审批详情全宽 |

页面根容器不得横向溢出；复杂表格可在自己的容器横向滚动，图谱在画布内平移。Grid/Flex 子项设置 `min-width: 0`，长 ID 可换行，完整查询和 JSON 放在独立滚动区域。

上表是常见视口的体验指引，具体分栏仍以容器规则为准。200% 缩放时按实际 CSS 视口重新排版，例如 1920px 屏幕可能只有约 960 CSS px，不能仍渲染桌面三栏。顶栏缩窄后保留连接/健康状态文字与入口，完整时钟、用户名等可在对应入口展开查看；状态栏不得挤出视口。

### 5.4 横向流程与历史记录

六角色调查进度、审批流程、模拟响应进度均从左到右排布，不改成上下交错的流程。六角色摘要可采用约 800px 的最小内容宽度；不足时只在步骤条模块内横向滚动，首次定位当前步骤，并提供“第 n / 6 步”和完整文字列表。不可通过裁切隐藏后续步骤，也不靠缩小字号维持横向。

近期活动与审批记录是历史事件，允许纵向时间轴；它们不属于工作流步骤组件。重试与并行任务显示实际状态，六角色横向摘要不意味着后端总是严格串行。

普通内容重排应消除页面级横向滚动；表格和攻击图等确需二维查看的内容在各自模块滚动，并提供等价的易读查看方式。本稿另要求 200% 缩放实测；这不等于已完成 WCAG Reflow 的全部验收。[W3C 重排说明](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 6. 各页面的具体设计

### 6.1 运营总览

```text
┌────────────── 通栏：连接 / 源健康摘要 / 模式 / 时间 / 用户 ─────────┐
│ 导航 │ 标题：运营总览       时间范围 [最近24小时] [刷新]           │
│      │ [待处理告警] [高危调查] [运行中调查] [待审批方案]           │
│      │ ┌──────── 告警趋势（8列） ───────┐ ┌── 状态分布（4列） ──┐ │
│      │ └───────────────────────────────┘ └──────────────────────┘ │
│      │ ┌──── 最近告警（8列） ───────────┐ ┌── 近期活动（4列） ──┐ │
│      │ └───────────────────────────────┘ └──────────────────────┘ │
│      │ 数据源健康：日志源状态 / 最后入库 / 索引延迟                │
└─────────────────────────────────────────────────────────────────┘
```

采用 12 列 Grid。第一行 4 个指标等宽，第二、三行使用 8:4；内容容器不足 1200px 时图表与列表改上下排列，指标按 2×2 排列。趋势图建议高 280px，告警表首屏展示 6～8 行，每行保留严重性标签和可打开详情的标题。

默认时间窗口最近 24 小时，可选 1 小时、7 天和自定义；顶层指标与图表使用同一时间窗口。待处理数量属于“截至窗口结束时”的状态量，趋势属于窗口内发生量，接口和标签明确区分。

指标口径由后端聚合，不从当前分页列表推算：待处理告警需要后端提供处理状态；高危调查按去重 incident 计数；运行中调查排除等待人工；待审批方案只计当前有效、未决定版本。没有处理状态时第一版将指标改名为“窗口内告警”，不伪造“待处理”。

告警趋势默认折线图，调查状态使用横向条形图。总告警系列采用浅蓝，严重/高危聚合采用浅红；图例区分统计系列，不代表每条告警的风险。系列数量保持可读，图例支持过滤；没有必要时不再增加饼图或装饰仪表盘。近期活动使用事件时间轴。点击指标或图形进入带筛选的列表，同时保留时间范围。显示统计口径、最后更新时间和真实 0；未获得数据、无权限或服务异常显示相应状态，不能替换成 0。

数据源健康与 `/health/live` 分开：进程存活不表示日志仍在入库。第一版先展示可核实的 PostgreSQL/OpenSearch 就绪状态，以及各日志源最近入库时间与延迟；未知状态明确为“未获得健康数据”。

全局顶部始终显示简洁健康摘要，例如“数据源 4/5 正常 · 1 延迟”；首页下方健康状态条展示各源、入库时间与延迟详情。两者使用同一读模型与更新时间，不分别计算两个“健康率”。当可核实的接入数量未知时不展示虚构的分母。

### 6.2 告警列表和详情

列表过滤器：时间、严重性、处理状态、关键词；只有后端支持的来源/实体字段才启用筛选。输入关键词 300ms 防抖，显式筛选即时生效，改变筛选后回到第一页。默认每页 20 条，可选 50/100，按创建时间倒序。

表格列：严重性、标题、来源摘要、首次/创建时间、关联实体、处理状态、调查入口。来源摘要与实体由后端告警读模型提供；当前 Alert DTO 没有这些字段，第一步可先展示已有字段，不从标题字符串猜测实体。

标题保留可访问的详情链接和分享路由；常规查看可在右侧详情抽屉打开，关联记录可用展开行，支持直接访问完整详情页。抽屉关闭后保留筛选、分页和滚动位置，避免每次查看都离开列表。“启动调查”是独立动作；主要提交在详情抽屉底部右侧。第一版不做批量启动。告警已经有关联调查时展示“继续调查”；是否允许另开调查由后端返回的可用动作决定。

详情页：上方展示告警摘要，下面分为“关联日志、调查记录”。证据原文作为文本/格式化 JSON 展示。启动按钮明确使用的规则或模型模式，提交后跳转到后端返回的 incident 与 investigation，不由前端临时生成业务 ID。

### 6.3 调查列表

表格列：调查编号、告警标题、严重性、当前阶段、证据数量、开始时间、验证结论、操作。支持运行中、待审批、待复核、已拒绝、完成、失败筛选；其中待复核和已拒绝为新增契约状态，在第 9 节规定落地方式。

调查列表以“当前有效 investigation”为主要记录；同一个 incident 的重试/历史运行通过详情查看，避免列表把一次事件的多次运行混为多个攻击事件。

### 6.4 调查工作台

```text
┌──────── 事件标题 / 风险 / 调查状态 / 数据同步 / 模式 ──────────────┐
│ 上下文               │ 攻击链工具条                         │证据│
│ 观察到的源 IP        │ 阶段筛选 / 图谱或列表 / 适应画布     │列表│
│ 入口主机与服务       │                                      │详情│
│ 分类候选 / ATT&CK    │          攻击行为关系图              │查询│
│ 时间 / 证据数量      │                                      │哈希│
│ 响应摘要与入口       │                                      │校验│
│                      ├──────────────────────────────────────┤    │
│                      │ 六角色横向进度 + 完成时间 + 执行记录 │    │
│                      │                      [查看响应方案] │    │
└──────────────────────┴──────────────────────────────────────┴────┘
```

上下文区字段：事件编号、观察到的源 IP、入口主机、入口服务、首次观察时间、攻击类型候选、ATT&CK 技术、规则/模型置信度和证据数量。字段使用紧凑键值排版，长内容展开查看。置信度标明来源、适用结论和计算依据；规则未提供可信分数时显示“未提供”，不自行生成百分比。来源未知使用“未知”；不将源 IP 表述为真实攻击者身份。

事件标题行同时显示执行状态和验证结果。返回与图谱辅助操作放在标题/工具条；“查看响应方案”等流程主动作放在主操作区底部右侧。批准/拒绝在方案详情完成，避免上下文不足时直接审批。

攻击链展示“发生了什么”；六角色展示“系统做了什么”。二者不能共用一张图。完整角色输出通过展开区域或详情面板查看，默认只显示六角色状态与当前阶段，不堆六段长文本，也不显示伪精确百分比。

横向六角色进度包含：分诊、证据收集、威胁分析、攻击链重构、响应决策、效果验证。每步展示状态图标、名称与真实完成时间；未完成用“运行中/等待/未开始”，不伪造完成时间。点击展开起止时间、摘要、错误和证据引用；重试显示当前 attempt 与历史记录。工具调用数仅在有实际审计数据时展示。效果验证等待人工审批期间显示“等待批准后执行”的 UI 说明，但不伪造已启动的 AgentRun。

### 6.5 响应队列与审批详情

队列默认展示待审批，另有已批准、已拒绝和验证记录标签。列表展示方案版本、调查、目标、风险、生成时间和审批状态。

详情页常驻“仅模拟处置”。桌面左侧详情与右侧决策区按 `7:3` 分配可用宽度，栏间距 16px；1920px 下约为 1254 / 538px，1440px 下约为 918 / 394px，1280px 下约为 806 / 346px（已扣栏间距，数值四舍五入）。决策栏建议不小于 320px；内容容器不足 1100px 时改为单列。

左侧自上而下为独立卡片：方案基本信息、拟执行动作表格、影响范围与风险、模拟回滚步骤、效果验证条件、证据引用、横向响应进度、模拟执行与验证结果。动作表格明确目标、操作、前置条件与预计影响；回滚仅展示模拟步骤和验证，不暗示已有真实封禁能力。

右侧人工决策卡展示方案版本、有效期、当前决策状态、必填理由、审批记录。左侧长内容自然滚动，右侧卡片 sticky 常驻；在给定可用高度内采用“可滚动内容 + 底部操作行”，按钮不放在滚动内容末端之外。理由、错误信息和审批记录均可访问，操作行固定在卡片底部右侧，不覆盖输入框。

为保证初次进入也能看到底部操作，桌面审批页的标题与模拟说明放在左栏，右侧决策卡从工作区顶部开始，不放在跨两栏的大标题下面。决策卡高度受视口可用高度约束；低于 700 CSS px 的短视口按自然布局处理，避免剩余空间不足以填写理由。

每页只保留一组决策提交按钮：“批准并开始模拟处置”和“拒绝方案”。批准使用青蓝主按钮，拒绝使用描边次按钮；拒绝不是故障状态，危险操作或错误才用红色强调。窄屏、短视口或 200% 缩放下取消固定决策栏，理由和操作置于正文末尾并保持右对齐。不能同时让全页悬浮按钮和决策卡按钮重复提交。

审批过程可横向显示“方案生成 → 人工决定 → 模拟执行 → 效果验证”；人工批准前后均采用真实状态。右侧审批记录则为历史时间轴，记录批准/拒绝、理由、身份、版本与时间。

批准前确认弹窗再次列出版本、目标、动作和模拟属性。**批准和拒绝均填写理由**：当前 ApprovalRecord 对所有决定的 reason 都要求非空，不能只对拒绝设必填。理由至少 1 个去除空白后的字符，前端建议上限 1000，后端同步约束。

点击提交后锁定当前按钮，保留输入。未知网络结果时先查询方案决策记录，确认是否已生效，再决定重试；方案版本变化或已被其他人决定时展示冲突，重新加载版本并要求重新确认。

“已批准”与“模拟执行完成”分开显示。验证结果严格区分成功、失败和证据不足，并展示时间窗口、条件、检查时间、引用证据和说明。流程完成不等于风险已解除。

## 7. 攻击链与证据交互规范

### 7.1 节点、连线和布局

业务节点表示攻击步骤，建议基础宽 240px、最小高 128px，固定核心区域并对长摘要截断。字段：阶段、行为标题、主机/服务、日志时间、模型置信度、证据数量以及事实/候选标识。来源实体作为节点内字段，不在第一版扩展成完整资产拓扑。

节点使用 8px 圆角矩形卡片、细边框和明确文字，不做发光边框。画布使用 canvas 深底色，点阵间距约 24px、点径约 1px，点色取装饰边框色；点阵只帮助定位，不能抢过节点和关系线。

默认从左到右布局，同阶段可以上下排列；初始阶段间距 64px，同层节点间距 24px，画布内边距 20px。Dagre 用于初始有向图布局，输入稳定节点 ID 和固定尺寸；复杂分组与跨组边属于 P1，再评估 ELK。React Flow 未内置通用自动布局引擎，需要显式接入布局库。[官方布局说明](https://reactflow.dev/learn/layouting/layouting)

连线必须标注语义：`temporal` 时间先后使用实线箭头，并标“时间先后”；`causal_candidate` 因果候选使用虚线箭头，并标“因果候选”；`related` 行为关联使用无方向点线并标“关联”。图例常驻，不能把“时间在后”画成已经证实的攻击因果。

边的线型表达关系类别；节点的实线/虚线边框表达事实/候选，两者在图例中分开说明。存在因果候选时不得因为节点已获得部分证据就把候选边改为时间实线。

初次加载执行一次布局与适应画布。证据增量、状态更新不重新排列全部节点；新节点加入时尽量保留旧位置。拓扑变化可提示“有新的攻击步骤”，由用户点击“重新布局”。节点拖动只改变本地展示位置，不能改变业务关系；不开放编辑连线、删除步骤和自由添加攻击事实。

工具条：放大/缩小、适应画布、阶段过滤、图谱/阶段列表、重新布局。阶段列表与图谱使用同一数据源，并提供相同证据入口。超大图先按阶段/主机筛选，默认不把几千条原始日志画成节点。

### 7.2 证据检查器

点击节点：选中节点并高亮直接关联步骤 → 显示引用证据列表 → 用户选择证据 → 显示详情。引用多条时不直接跳过证据列表。

详情包括：Evidence ID、关联 event ID、来源、观察时间、摘要、完整查询条件、SHA-256、引用它的步骤、后端校验状态与校验时间。长 ID 可截断显示但必须可复制完整值；哈希不能只留下不可恢复的省略字符串。

详情分为“摘要、原始日志、查询与校验”三个标签。原始日志必须来自新增的授权详情接口；现有 EvidenceItem 只有摘要与哈希，没有 raw。页面只展示服务端授权后的记录，不接受前端输入任意查询去访问数据库。

右栏/右抽屉内以等宽代码块展示日志片段、检索查询与哈希，块内独立横向滚动，可复制完整内容。抽屉始终从右侧进入；宽屏常驻检查器采用相同字段顺序与组件，切换形态不改变分析师查找证据的位置习惯。

日志证据与 ATT&CK 知识引用分开：日志用于支持发生事实，知识引用用于解释技术映射。知识条目显示技术编号、名称、版本和来源链接，不能冒充日志证据。

哈希存在显示“已记录内容哈希”；只有服务端在读取时核对规范化原始内容并返回结果，才能显示“本次校验通过”。原始文本的脱敏展示摘要不能直接与未脱敏原始事件哈希比较。

证据缺失或校验失败时保留节点和引用列表，显示明确原因，支持重试。校验异常阻止依赖该证据的方案审批，是否仍允许只读浏览由权限和后端策略决定。

## 8. 通用交互和内容状态

| 状态 | 页面表现 | 恢复方式 |
|---|---|---|
| 首次加载 | 与最终布局一致的骨架屏 | 数据到达后替换，避免整页跳动 |
| 无数据 | 说明当前窗口/数据源无记录 | 调整时间或检查接入 |
| 筛选无结果 | 展示筛选条件 | 清空筛选按钮 |
| 局部失败 | 该卡片内显示错误，其余区域保留 | 局部重试 |
| SSE 重连中 | 顶部连接提示，保留上次数据及同步时间 | 自动重连和快照校准 |
| 数据过期 | 明确“数据可能过期” | 刷新后恢复，暂停审批提交 |
| 401 / 403 | 身份过期 / 权限不足 | 重新认证 / 返回有权限页面 |
| 404 | 对象不存在或不对当前用户公开 | 返回列表，不伪造空详情 |
| 409 / 412 | 版本已变或已有决定 | 重取最新方案，重新确认 |
| 410 | 方案已过期，保留旧方案和输入，禁用审批 | 读取最新方案；只有服务端允许时才展示重新生成入口 |
| 服务端执行失败 | 展示阶段、原因及 trace ID | 查看失败记录；不会自动重跑处置 |

时区统一：API 使用带时区的 UTC ISO 时间，页面默认显示 Asia/Shanghai；时间窗口明示时区。图谱时间取日志观察时间，角色时间线取系统执行时间，两者不混用。

通知仅用于确认动作或提示需要处理的变化。普通状态刷新不重复弹 Toast；新证据增加显示数量，用户可继续阅读当前内容。表格刷新后不重置滚动位置与已选筛选。

键盘要求：按钮/链接可聚焦，节点有可访问名称，Escape 关闭模态面板，模态抽屉与弹窗管理焦点并在关闭后归还。非模态检查器不锁住整个页面的焦点。所有关键操作都有可见文字，不只使用图标提示。

图表提供文本摘要和可查看的数据表；画布提供阶段列表。状态、图例和线型至少通过两个通道表达。React Flow 提供可访问性能力，实施时保留并补全节点标签。[官方说明](https://reactflow.dev/learn/advanced-use/accessibility)

纵向滚动优先级统一：普通页面自然滚动；桌面常驻证据/决策卡可有独立内容滚动区；图谱平移、表格、横向流程与长代码仅在各自容器滚动。小屏不同时保留多个并排滚动区。固定顶栏与底部操作行不得挡住键盘焦点、最后一行数据、输入错误或当前步骤。

## 9. 前后端数据契约

本节的业务端点、扩展字段和事件恢复协议均是待实现提案。当前真实 HTTP 能力仅有健康存活检查。采用 FastAPI DTO 作为类型真源，定义后重新生成前端类型；展示模型可组合这些 DTO，但不另造同名且字段不同的业务类型。

| `POST /api/v1/alerts` | 告警接入；支持 Idempotency-Key | 规划 |
| `GET /api/v1/alerts` | 告警筛选和分页 | 规划 |

### 9.2 P0 需要补充的读取端点

| 新增接口 | 必要结果 |
|---|---|
| `GET /api/v1/alerts/{id}` | 告警详情、授权日志摘要、已有调查与可用动作 |
| `GET /api/v1/incidents` | 调查摘要列表、总量、分页与筛选 |
| `GET /api/v1/investigations/{id}` | 一致性调查快照、revision 与 stream_cursor |
| `GET /api/v1/incidents/{id}/evidence` | 当前事件授权证据列表、分页 |
| `GET /api/v1/incidents/{id}/evidence/{evidence_id}` | 证据详情、原始/脱敏日志、校验结果 |
| `GET /api/v1/response-plans` | 待审批/已决定方案分页队列 |
| `GET /api/v1/response-plans/{id}` | 方案完整详情、最新版本、审批及模拟/验证记录 |
| `GET /api/v1/dashboard/summary` | 指标、趋势、状态分布、数据源健康及窗口口径 |
| `GET /api/v1/data-sources/health`（新增提案） | 授权的全局健康摘要与源列表：源标识、状态、最近入库、延迟、checked_at、过期判定 |
| `GET /api/v1/session` | 当前服务端身份与允许动作 |

全局顶部与首页健康模块共用 data-sources/health 查询缓存；dashboard/summary 中若保留健康摘要，也必须来自同一后端健康服务，不能作为第二份 UI 状态。健康状态至少区分正常、延迟/降级、失败、未知，健康检查过期时显示“数据可能过期”。刷新频率和延迟阈值由实际源配置决定，不用前端时钟推导实时健康。

第一版列表采用 page/page_size，page_size 限制 20/50/100；统一返回 `items / total / page / page_size`。分页、排序和筛选在服务端执行。高流量实时列表的 cursor 分页属于 P1，不混用两种分页模式。

告警窗口查询采用 `time_from / time_to / severity / handling_status / query`，时间区间约定左闭右开。调查列表另有 `status`；响应队列另有 `decision_state`。后端白名单处理 sort，不把前端传来的列名直接拼接成 SQL。

`POST investigations` 请求明确 `alert_id` 和 `mode: rules | model`，使用 Idempotency-Key；服务端返回状态是否新建以及两个业务 ID。rules 模式从原始演示日志生成结果并执行同样的证据与审批检查，不读取评分真值。

### 9.3 调查快照

快照是前端页面恢复的权威读模型；至少包含：

| 字段 | 类型/语义 |
|---|---|
| `investigation_id / incident_id / trace_id` | 当前运行、事件与追踪标识，互不替代 |
| `revision` | 十进制字符串，单调递增的快照版本 |
| `stream_cursor` | 与快照同一一致性视图下的最后事件游标 |
| `updated_at / mode / available_actions` | 更新时间、运行模式、服务端可用动作列表 |
| `incident / alert` | 案件与告警摘要；有实际来源才扩展实体信息 |
| `agent_runs` | 真实运行记录，含稳定 role_key、attempt、状态、时间、输出摘要、证据引用和错误 |
| `origin / classification` | 空值或当前结论；区分未知与已支持 |
| `knowledge_refs` | ATT&CK 知识引用，含知识条目 ID、技术 ID、名称、知识版本、来源链接与检索时间 |
| `attack_graph` | 节点、边、图版本与生成时间 |
| `evidence_summary` | 证据总数与首批授权摘要；全量使用证据分页接口 |
| `response_plan / approval / simulation / validation` | 当前方案和结果，可为空；大字段允许详情按需获取 |
| `review` | required、reason、回退次数；持久化人工复核原因 |
| `error` | 当前失败信息，含 code、message、trace_id |

revision 和事件序号不用 JS Number 表示超大整数；序号比较可使用 BigInt，游标本身视为服务端生成的不透明字符串。

六角色的稳定 role_key 为 `triage / evidence_collection / threat_analysis / attack_reconstruction / response_decision / validation`。每次真实重试增加 attempt 并创建新 run_id；时间线保留历史记录，不把同一角色的多次运行覆写成一个结果。

knowledge_refs 是独立知识引用 DTO，不放进 EvidenceItem。服务端仅返回本次调查实际检索并授权的条目，使用知识 ID 校验结论引用；URL 只允许可信知识来源，不接受日志中提供的任意外链。知识版本表示 ATT&CK 数据集版本，不等同于快照 revision。

事件状态保留现有 received、triaged、collecting、analyzing、reconstructing、awaiting_approval、simulating、validating、completed、failed；**新增提案**为 `needs_review` 和 `rejected`。前者表达证据回退一次后仍不足，后者表达拒绝后停止。新增状态需同步模型、数据库约束、迁移、状态转换测试和生成类型，不能仅在 UI 加标签。

`unknown` 是结论质量，不是调查阶段；新增 `conclusion_status: supported | unknown` 与 `unknown_reason` 表达来源/分类不足。AgentRun 保持现有四种执行状态；未生成 run 的角色用前端展示“未开始”，人工等待由调查状态解释。

工作流合法路径包括：正常完成；批准前等待；拒绝进入 rejected；第二次证据不足进入 needs_review；系统错误进入 failed。验证 outcome 为 failure/insufficient_evidence 时允许流程 completed，但页面同时展示该结果。第一版不提供“取消调查”，因为现有 HTTP 层没有完整取消能力。

### 9.4 攻击图展示 DTO

现有数据库 attack_steps 具有步骤、序号、阶段、技术、描述、时间与证据引用，但还不是公开攻击图 DTO。需要补充如下读模型。

| 对象 | 最小字段 |
|---|---|
| 节点 | step_id、sequence、phase、description、host、service、observed_at、technique_ids、confidence、evidence_ids、support_status |
| 边 | edge_id、source_step_id、target_step_id、relation、description、confidence、evidence_ids、support_status |
| 图 | revision、generated_at、nodes、edges |

`support_status` 为 `supported / candidate / insufficient`。缺失主机、时间、技术或置信度用 null，不能补造；候选有证据引用也要显示候选。后端检查引用属于当前事件、边两端存在以及自引用/重复关系；图允许不完整链路。前端布局不决定攻击事实。

### 9.5 证据详情 DTO 与哈希

响应为 `evidence + raw_event + raw_access + integrity`。其中 evidence 基于当前 EvidenceItem，raw_access 为 full/redacted/denied；integrity 包含 algorithm=sha256、canonicalization=evidencesoc-json-v1、status=verified/mismatch/unavailable、checked_at。

原始事件哈希由后端规范化 JSON 计算：键排序、紧凑分隔符、UTF-8、不转义非 ASCII、拒绝 NaN。它不是原始文件字节的哈希，浏览器普通 JSON.stringify 不保证等价。详情接口关联 event_id，在当前事件授权范围内读取并重新核验，然后按权限脱敏返回。

校验失败时 HTTP 可返回明确错误体或可读的异常详情，但必须禁止显示绿色 verified。evidence_id 全局存在不能替代事件归属与用户权限校验。

### 9.6 响应方案与审批契约

现有 `actions: list[dict]` 必须定型。方案详情新增 plan_version、execution_mode=simulation、risk_level、risk_reason、affected_assets、business_impact、expires_at、actions、rollback_steps、validation_checks、evidence_ids。

动作包含 action_id、白名单 type、target、parameters、expected_effect、risk、rollback_ref 与 evidence_ids。回滚与验证步骤有稳定 ID、说明、目标、预期结果和证据/查询范围。第一版是安全模拟，页面上的回滚计划不表示已经具备真实回滚执行器。

审批请求正文为 `plan_version + reason`，附带 Idempotency-Key；decided_by 从已验证会话取得。服务端在事务中校验权限、当前版本、到期状态、已决定状态和证据有效性，记录决策后再恢复工作流。

相同 key 与相同请求返回原结果；相同 key 不同正文返回 409；版本冲突返回 409/412；方案过期返回 410。网络超时不能自动发送新的审批 key，先读取方案结果。按钮点击不能在前端直接把状态推进到 simulating。

模拟执行与验证分别定型为新增读模型，不能由审批成功推断执行成功：

| 对象 | 必要字段 |
|---|---|
| `simulation` | simulation_id、response_plan_id、plan_version、status、started_at、finished_at、action_results、error |
| 单项 `action_result` | action_id、模拟结果 success/failure/skipped、说明、开始/结束时间 |
| `validation` | 保留现有 ValidationResult；增加 time_from、time_to、checks |
| 单项 `validation_check` | check_id、检查条件、outcome=success/failure/insufficient_evidence、evidence_ids、说明 |

simulation.status 为 pending/running/completed/failed；completed 表示所有模拟步骤结束，逐项是否成功由 action_results 决定。simulation/validation 为 null 表示尚未执行；验证窗口只使用真实查询窗口，不采用报告生成时间代替。与方案相关的结果必须关联被批准的同一 plan_version。

普通查询失败采用最多两次有间隔的重试；审批、启动调查等写请求不采用盲目自动重试。服务端统一错误体含 code、message、trace_id、可选 field_errors；失败时用户输入保留。

## 10. SSE、缓存与恢复协议

### 10.1 同源接入

浏览器访问同源 `/api/v1/*`；本方案采用 Next.js Route Handler 代理到 FastAPI，路径白名单、服务端后端地址和会话转发集中管理。普通 API 代理与 SSE 代理分开实现，SSE 不经过 JSON 解析或普通超时中间件。

FastAPI 持有真实权限、证据和状态约束；Next 代理不能成为绕过后端校验的第二套业务逻辑。后端地址保留在服务端环境，不放入 NEXT_PUBLIC 字段。

会话推荐同源 HttpOnly Cookie，浏览器无需将 token 放到 SSE URL。原生 EventSource 无法设置任意 Authorization header；如果未来切换 bearer 模式，就由代理注入或采用 fetch 流客户端，不拼接长期凭据到 query。

SSE 代理以流持续转发，客户端断开时取消上游请求；不得缓冲全量响应。部署返回 text/event-stream、no-cache/no-transform，停用代理缓冲，心跳间隔需小于空闲超时。

### 10.2 事件类型和负载

保留准备书中的 9 类事件，并明示增加 4 个恢复/状态事件。

| 事件 | 处理方式 |
|---|---|
| `investigation.started` | 更新开始时间与快照版本 |
| `agent.started` | 合并 run_id/attempt 的执行记录 |
| `evidence.added` | 按 evidence_id 合并摘要、失效证据列表查询 |
| `agent.completed` | 合并角色结果，失效调查快照以取得分类/图更新 |
| `approval.required` | 展示人工等待，失效响应队列与方案查询 |
| `decision.recorded` | 读取服务端决策，更新版本和可用动作 |
| `validation.completed` | 更新独立验证结果，不直接推断流程终态 |
| `investigation.failed` | 显示系统失败并读取最终快照 |
| `investigation.completed` | 读取最终快照，再关闭连接 |
| `investigation.review_required`（新增） | 显示 needs_review，暂停自动调查 |
| `investigation.rejected`（新增） | 显示 rejected 与理由，读取终态并关闭连接 |
| `stream.reset`（新增控制事件） | 游标失效，重读快照并重新建立连接 |
| `stream.heartbeat`（新增控制事件） | 供客户端检测连接活动，无持久化事件序号，不更新游标 |

持久化业务事件信封包含 schema_version、event_id、sequence、investigation_id、incident_id、revision、trace_id、occurred_at、payload。事件类型使用 SSE event 字段，id 与 event_id 一致。序号按 investigation 单调递增。

reset 与 heartbeat 是不进入持久业务序列的控制消息：不发送 id、不改变 Last-Event-ID、不参与序号缺口判断，负载仅包含 schema_version、investigation_id、occurred_at 与控制信息。reset 在游标失效后发送并结束该连接；heartbeat 每 15 秒发送，用于可观察的活动计时。

SSE 只包含必要的摘要和结构化业务变化，不推送原始日志、秘密信息或模型内部思维过程。未知 schema 或类型触发重新同步并记录协议异常，不静默丢掉后继续假定状态正确。

### 10.3 无漏更新的恢复过程

1. 获取调查一致性快照以及游标 C；后端保证状态和对应事件在同一事务或事务 outbox 中持久化。
2. 新连接请求 `/stream?after=C`；服务端首先补发 C 之后的记录，再接实时流，避免快照和订阅之间漏事件。
3. 浏览器同一 EventSource 自动重连时由 Last-Event-ID 恢复；服务端规定 header 优先于初始 after 参数。刷新页面后重新获取快照。
4. 前端按 event_id 去重，按 investigation_id 隔离。过旧 revision 不覆盖较新状态；检测到序列缺口时重取快照。约定同一调查事件流无筛选、序列连续。
5. 游标超出保留期时发送 stream.reset；前端关闭旧连接，重取快照，再从新游标订阅。不能直接跳到最新状态而保留旧图谱。
6. 每 15 秒发送 stream.heartbeat；服务器也可发送不带 id 的 SSE 注释维持代理连接，但注释不触发浏览器 message，不能用它单独实现前端活动计时。30 秒未有可观察活动时，watchdog 标记数据可能过期，关闭旧 EventSource，校准会话/快照后从新游标建立一个连接；若请求仍失败，保持离线并按有上限的退避重试校准。
7. 运行终态后获取最终快照并关闭连接。待审批和待人工复核属于业务等待，不标记网络错误。

连接提示独立于调查状态。重连/离线时保留旧内容，审批提交暂停；快照成功校准、会话有效且 available_actions 允许后再恢复按钮。普通 onerror 由原生 EventSource 重连；仅 reset、协议错误、watchdog 活动超时或用户主动刷新执行主动重建，重建前必须关闭旧连接并清理计时器，避免同时启动第二套循环。

代理收到 401/403 或永久性协议错误时不得无限重试。EventSource error 不能直接向前端提供 HTTP 状态，因此 onerror 与 watchdog 触发限频的 `/session` 和快照校准：401 关闭订阅并进入重新认证状态；403 停止订阅当前对象并显示权限不足；只有网络失败继续恢复。校准检查至少间隔 5 秒，避免每次原生重连触发多个身份请求。

heartbeat 重建的校准失败采用 1/2/4/8/16/30 秒退避并限制最多 8 次，之后停在明确的离线提示，提供手动重试。会话恢复前审批保持禁用；恢复订阅前重新检查 available_actions 与方案版本。

### 10.4 React Query 与前端状态边界

服务端数据由 Query 管理：告警、调查快照、证据详情、方案与运营指标。查询 key 包含业务 ID、用户会话作用域、筛选和时间窗口，防止切换用户后复用别人的数据。

局部 UI 状态使用 React state/reducer：节点选中、抽屉标签、图谱位置、折叠和审批输入。全局只保留主题、当前会话和连接状态；第一版不另加 Redux/Zustand，避免同时维护两份服务器数据。

SSE 更新按 100～250ms 批量合并，重要人工决策提示立即显示；合并证据/run 时按稳定 ID 去重。角色完成等结构变化触发快照刷新，快照请求合并去重，较旧响应不得覆盖新 revision。

页面切换时关闭 EventSource、取消无用请求；Strict Mode 下 Effect 必须清理订阅。后台标签页不渲染密集动画；重新可见时重新校准快照。退出会话清空敏感 Query 缓存。

## 12. 图表、性能与可观测性

ECharts 按需引入 Line/Bar、Grid、Tooltip、Legend、DataZoom、Aria 与所选渲染器，默认 SVG 适合第一版的中小规模统计图；如果实际数据量要求 Canvas，按性能测量切换。官方支持按需引入，避免直接打包全部图表。[导入说明](https://echarts.apache.org/handbook/en/basics/import/)

图表与图谱按路由延迟加载，首页不加载 React Flow。EChart 封装统一处理容器尺寸、ResizeObserver、初始化、setOption 和 dispose；隐藏标签页恢复时校准尺寸。切换图表不可泄漏 DOM、实例和观察器。

图表启用可访问性组件，提供人工编写的简短中文摘要；颜色相近的系列可增加纹理，数据表提供同一筛选口径。[ECharts 可访问性说明](https://echarts.apache.org/handbook/en/best-practices/aria/)

性能验收预算是目标，不是当前测量结果：

| 场景 | 目标与测量条件 |
|---|---|
| 普通 API | 无模型调用时本机 P95 < 500ms；计时含后端处理 |
| 首个 SSE | 创建调查后 2 秒内收到 started；不把模型生成耗时混入 |
| 典型攻击图 | 50 节点/80 边时布局后可交互 < 1 秒，平移/缩放无持续卡顿 |
| 扩展图 | 200 节点/300 边仍可选中和打开证据；布局 > 100ms 时移至 Worker |
| 高频事件 | 10 事件/秒持续 60 秒，不重复、不丢状态，不导致页面冻结 |
| 大列表 | 服务端分页，首次 20 条；长 JSON > 1MB 分段/折叠展示 |
| 长时间查看 | 多次进入退出调查与打开关闭图表后，无残留连接和不断增长的实例 |

记录测试设备、浏览器、数据规模和后端模式，避免给出与硬件无关的性能保证。生产构建的首页资源体积记录为基线，后续每次增加图表/库对比增量；不预先承诺未经测量的首屏分数。

失败消息显示可复制 trace ID；普通浏览器日志不打印完整原始证据、Cookie 或密钥。第一版使用后端本地审计/结构化日志和 Playwright Trace，不依赖付费遥测服务。

## 13. 身份、权限和业务约束

六个 Agent 角色是工作流节点，不是六种用户权限。用户权限单独按动作划分：查看、启动调查、审批、管理接入。前端隐藏或禁用按钮改善体验，后端再次校验会话和事件归属。

P0 本地演示采用服务端固定的演示账户与会话；只有受限本机环境可使用明确的开发会话入口，不通过任意客户端字段决定审批人。浏览器同源 Cookie 采用 HttpOnly 和适当 SameSite，非本机部署启用 Secure；写请求校验 Origin/CSRF。对外或多人部署前落实 P1 正式认证和角色管理。

后端提供 available_actions 与拒绝原因，UI 无权将 MCP 工具白名单解释为用户鉴权。不能让浏览器直接连接 OpenSearch、数据库或 MCP Server。

响应只允许模拟；前端文案、按钮、报告和后端 execution_mode 一致。不存在真实封禁、账号禁用或主机隔离入口。审批审计记录方案版本、动作、理由、身份、时间与 trace ID。

日志、模型摘要和知识内容都按不可信文本处理；原文和 JSON 使用文本节点。第一版无需 HTML/Markdown 渲染，不使用 dangerouslySetInnerHTML。下载内容由授权接口生成。

正式调查不读取 labels、attacks.log 或评分真值；评测页面仅展示评分程序输出的汇总/授权明细，调查 API 与评测 API 的数据权限分离。规则模式能完成业务流程，不代表已证明模型具有同等识别效果。

## 14. 免费演示、Mock 与真实集成

三种数据运行方式必须区分并在页面常驻标识：

| 方式 | 数据与执行 | 用途 |
|---|---|---|
| 前端测试样例 | 本地 fixture + HTTP/SSE 测试拦截，不运行真实后端工作流 | 并行开发 UI 和可重复测试；显示“界面样例” |
| 规则演示 | 本地真实后端、样例原始日志、规则工作流与真实证据/审批 | 无付费 API 也能完整演示；显示“规则演示” |
| 模型调查（可选） | 经过配置的本地或外部模型，真实工具和工作流 | 功能增强与效果评估；外部付费模型不属于必需项 |

断网时可以使用已准备好的本地后端与规则数据；后端不可用时只能切到明确的界面样例。界面样例不能偷偷替换真实调查结果，也不能把前端按钮动画当成模拟处置实际执行。

至少准备六套固定验收场景：正常批准闭环、审批拒绝、第二次证据不足、证据校验异常、断线重连和审批版本冲突。前端样例不读取测试环境秘密，不将 mock 端点开放成生产服务。

本地自托管为默认交付路径：使用现有 Node.js、FastAPI、PostgreSQL 和 OpenSearch；不要求 Vercel、商业托管数据库或第三方测试平台订阅。容器不是前端运行的必要条件；如果使用现有 Compose 环境，采用符合自身环境许可的容器运行时，不把 Docker Desktop 对所有用户都免费的假设写入成本承诺。

## 16. 测试策略与完成条件

### 16.1 自动化验收

| 范围 | 场景 | 预期 |
|---|---|---|
| 端到端正常路径 | 告警 → 调查 → 六角色 → 节点证据 → 批准 → 模拟 → 验证 | 全过程 ID 与证据一致，最终显示实际结论 |
| 审批边界 | 批准前、拒绝、重复点击、空理由、方案变更 | 未批准不执行；空理由被拒；相同 key 不重复决定 |
| 方案过期 | 打开前已过期、确认弹窗停留期间到期 | 后端拒绝旧方案，UI 保留上下文并禁用审批，提示最新方案 |
| 未知结论 | 第二次收集仍不足 | needs_review 与原因可见；不自动判为安全 |
| 证据可信性 | 缺失引用、跨事件 Evidence ID、哈希不一致 | 后端拒绝/标异常，页面不显示绿色校验通过 |
| 恢复 | 断线期间产生新事件，重连/刷新 | 最终快照一致，无漏步骤、重复证据或角色记录 |
| 过期游标 | SSE 游标已清理 | reset 后重读快照，旧数据不继续用于审批 |
| 数据隔离 | 调查 A 切到 B 后收到 A 的迟到事件 | B 状态不被修改 |
| 并发决策 | 两会话批准/拒绝同一版本 | 仅一次决定，另一会话看到冲突与最新状态 |
| 规则演示 | 无模型密钥、可选关闭外网 | 真实本地后端走完整闭环，并保留规则标识 |
| 图表交互 | 点击指标/图表下钻 | 查询窗口、筛选与列表保持相同口径 |
| 无权限/异常 | 401/403/404/500/超时 | 有明确状态和恢复方式，不清空已加载有效内容 |

Vitest 重点验证 reducer 去重、revision 顺序、序号缺口与 graph 支持语义转换；API 权限/事务/哈希由后端集成测试验证，不能只靠前端拦截测试证明。

Playwright 通过角色、名称、文本和稳定 test ID 定位按钮、节点与证据。图谱测试“点击节点打开正确证据”的行为；统计图验证数据摘要和下钻结果，不以不稳定的像素坐标作为主断言。[官方最佳实践](https://playwright.dev/docs/best-practices)

### 16.2 视觉与可访问性验收

- 1920×1080、1440×900、1280×800、1024×768、390×844 均无页面级横向溢出；图谱、表格和横向步骤条仅允许局部滚动。
- 默认深色覆盖表格、表单、抽屉、通知、确认弹窗、图谱和图表。
- 中性背景仅三级；卡片圆角 8px、1px 边框；实际计算样式无外投影、玻璃模糊、霓虹、纯黑/纯白视觉填充，允许规范中定义的弱内侧边线。

- 调查宽屏按 3:6:3 计算；容器不足时切换两栏/抽屉或单列，不继续压缩画布。审批按 7:3 与最小决策栏宽度重排。

- 键盘可完成筛选、选择证据、填写理由和审批；移动端触控尺寸合适。
